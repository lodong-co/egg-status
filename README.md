# egg-status — 에그호스팅 공개 상태 페이지

서비스별 운영 상태를 **에그호스팅 인프라 밖에서** 측정해 공개한다.
새 계정도, 비용도 들지 않는다 — GitHub Actions(측정) + GitHub Pages(페이지)만 쓴다.

## 왜 밖에서 재는가 (실측 근거)

2026-08-01, egg-api 가 **9시간 30분** 동안 HTTP 요청을 한 건도 처리하지 못했다.
그런데 그 구간의 내부 감시 지표는 **96.429%** 로 전날·다음날과 소수점까지 같았고,
텔레그램 알림도 15:11 이후 10시간 동안 egg-api 관련 건이 **0건**이었다.

감시 주체(내부 TCP 체크, 알림 디스패처)가 **죽은 대상 안에** 있었기 때문이다.
그래서 이 측정은 우리 DC 와 접점이 0인 GitHub 러너에서만 돈다.

## 구조

```
GitHub Actions (10분 cron)
   └ scripts/probe.mjs   5개 컴포넌트 프로브 → docs/state.json 갱신 → 커밋
GitHub Pages (main /docs)
   └ docs/index.html     state.json 을 읽어 상태 표시
status.egghosting.com    NameSilo DNS 에 CNAME → <org>.github.io
```

### 감시 대상 5줄

| 컴포넌트 | 프로브 대상 | 비고 |
|---|---|---|
| 관리 콘솔 | `egghosting.com/api/public/status` | 무인증 공개 헬스. **DB 왕복 1회 포함** |
| 웹호스팅 | `sajuj.com` | 카나리 |
| 클라우드 서버 | `hrdlo.kr` | 카나리 |
| 도메인 | `eggdomains.com` | 자체 권위 DNS 의존 |
| 로그인 | `ldpass.com` | 자체 권위 DNS 의존 |

**카나리란**: 고객 사이트를 개별로 잴 수 없으므로, 유료 고객과 **같은 경로**
(공인 IP → FortiGate → 앞단 nginx → 컨테이너)를 타는 우리 자체 서비스를 대신 잰다.
우리 소유라 고객 동의 문제가 없다.

🔴 **관리 콘솔은 홈(`/`)이 아니라 API 를 찔러야 한다.** 2026-08-01 당시 홈은 webvip 를 보고
살아 있었고 API 만 죽은 노드에 고정돼 있었다. 홈만 찌르는 프로브는 그 9시간 30분을 통째로
놓친다.

## 설치

### 1. 레포 + Pages

```bash
gh repo create <org>/egg-status --public --source=. --push
gh api -X POST repos/<org>/egg-status/pages \
  -f 'source[branch]=main' -f 'source[path]=/docs'
```

### 2. DNS (NameSilo)

`egghosting.com` 의 권위 DNS 는 NameSilo(dnsowl)다. 여기에 한 줄 추가한다.

```
Type      CNAME
Hostname  status              ← 라벨만. "status.egghosting.com" 아님
Target    <org>.github.io     ← 레포 이름은 들어가지 않는다
TTL       3600                ← NameSilo 최소값 (300 넣으면 code280 거부)
```

전파 2~3분. 확인: `nslookup status.egghosting.com 8.8.8.8`

### 3. 커스텀 도메인 연결

```bash
gh api -X PUT repos/<org>/egg-status/pages -f cname=status.egghosting.com
```
GitHub 이 DNS 를 확인한 뒤 Let's Encrypt 인증서를 자동 발급한다(수 분~1시간).
발급되면 Settings → Pages 에서 **Enforce HTTPS** 를 켠다.

⚠️ **순서를 지킬 것.** DNS 를 먼저 넣지 않고 커스텀 도메인을 설정하면 인증서 발급이 실패한다.

## 함정

**① 와일드카드를 덮어쓴다 — 정상 동작이다.**
`A * → 210.207.108.133` 이 이미 있어 지금 `status.egghosting.com` 은 우리 DC 로 간다.
명시적 CNAME 을 넣으면 더 구체적인 레코드가 이겨 GitHub 으로 간다.

**② 🔴 `status` 라벨을 고객 서브도메인 발급에서 예약어로 막을 것.**
고객이 `status` 를 집어가면 앞단 nginx 에 vhost 가 생겨 충돌한다.
라벨 발급에 DB 유니크 제약이 없고 앱 레벨에서만 걸러진다.

**③ GitHub schedule 은 정확하지 않다.**
러너가 붐비면 늦거나 건너뛴다. 그래서 10분은 "정확히 10분"이 아니라 "대체로 10분"이다.
가동률을 공개할 단계가 되면 외부 프로버로 옮기는 편이 낫다 —
`cloudflare/worker.js` 에 Cloudflare Worker 대안 구현이 들어 있다(cron 이 정확함, 계정 1개 필요).

**④ 60일간 커밋이 없으면 GitHub 이 scheduled workflow 를 자동 비활성화한다.**
이 레포는 10분마다 커밋되므로 해당 없음.

## 운영

### 가동률 %(90일) 공개하기

수집은 첫날부터 계속되지만(`docs/state.json` 의 `daily`) 화면에는 안 나온다.
공개하기로 결정하면 `docs/index.html` 의 렌더 함수에 열을 추가한다.

🔴 공개 전에 **보상 기준을 먼저 문서화**할 것. 숫자를 공개하는 순간 SLA 로 읽히고
환불 근거가 된다. 현재 MRR 의 79% 가 단일 고객(전용서버)에 몰려 있어 노출이 크다.

### 컴포넌트 추가/변경

`scripts/probe.mjs` 의 `TARGETS` 배열만 고친다. 배열 순서 = 페이지 표시 순서.

## 무슨 색으로, 왜 그런지

하루치 점검을 접어서 한 칸을 칠한다. 기준은 **성공률**과 **응답 속도** 둘 다다.

| 색 | 조건 | 라벨 |
|---|---|---|
| 초록 | 다 뜨고, 느린 응답도 10% 미만 | 정상 |
| 노랑 | 성공률 95~100% **또는** 느린 응답 10% 이상 | 성능 저하 · 응답 지연 |
| 주황 | 성공률 50~95% | 부분 장애 |
| 빨강 | 성공률 50% 미만 | 전체 장애 |
| 회색 | 잰 적 없음 | 측정 없음 |

**200 이라고 다 정상은 아니다.** 트래픽이 몰려 8초씩 걸리는 날도 응답 코드는 200 이라,
성공/실패만 세면 그런 날이 초록으로 보인다. 그래서 `SLOW_MS`(4초)를 넘긴 성공을
따로 세고, 그런 응답이 하루의 10% 를 넘으면 노랑으로 칠한다.
GitHub 러너에서 한국까지 왕복이라 평소가 0.7~1.4초다. 여기에 여유를 두고 4초로 잡았다.
10초를 넘으면 그건 타임아웃이라 실패로 접힌다.

**원인은 하루치에 같이 쌓는다.** `daily[id][날짜].fails` 에 사유별 횟수가 들어가고,
막대에 마우스를 올리면 사람 말로 나온다 — `응답 없음(시간 초과) 3회 · HTTP 502 2회`.
예전에는 실패 횟수만 세고 왜 실패했는지는 어디에도 안 남겨서, 지난 장애의 원인을
물으면 답할 데이터가 없었다.

사유는 `timeout · dns · refused · reset · tls · network · http-<코드>` 로 접는다.

## 점검 주소가 틀렸을 때 (측정 불가)

**아직 한 번도 200 을 받은 적 없는 컴포넌트가 404/405 를 내면 장애로 세지 않는다.**
그건 서비스가 죽은 게 아니라 우리가 점검 주소를 잘못 겨눈 것이다.
측정에서 빼고(회색) 러너 로그에 경고를 찍는다. 초록으로 칠하지는 않는다 —
그 시간의 상태를 우리는 모른다.

한 번이라도 200 을 받은 뒤의 404 는 **그대로 장애로 센다.** 라우팅이 깨진 것일 수 있고,
그런 진짜 장애를 이 규칙이 가려서는 안 된다. 기준은 컴포넌트의 `firstOkAt` 이다.

> 실제로 2026-08-19~20 에 관리 콘솔이 그랬다. `/api/public/status` 가 배포되기 전이라
> 프로브가 404 를 받았고, 멀쩡한 이틀이 「전체 장애」 로 칠해졌다.
> 같은 기간 나머지 4개는 전부 100% 였다 — 회선이나 DC 문제였다면 같이 떨어졌어야 한다.

## 손으로 바로잡기 (`corrections`)

측정이 틀렸다고 **조용히 고치면 그 상태판은 못 믿는다.** 고쳤으면 고쳤다고 남긴다.

`docs/state.json` 의 `corrections` 에 한 줄 넣으면 그 칸 툴팁에 「보정됨」과 이유가 뜬다.
프로브는 이 배열을 만들지도, 지우지도 않고 그대로 이어받는다.

```json
{ "component": "console", "day": "2026-08-19",
  "reason": "점검 주소 오류 — 헬스 엔드포인트 배포 전이라 404. 장애 아님",
  "at": "2026-08-26T00:00:00.000Z" }
```

같은 날 `daily` 의 숫자도 같이 고친다. 실패 횟수는 `fails` 에 원인과 함께 남겨 둔다.

## 화면 확인

색·툴팁·원인 표시는 눈으로 봐야 안다. 브라우저를 직접 몰아서 본다.

```bash

```

## 이 페이지가 하지 않는 것

- **개별 고객 서비스 상태를 보여주지 않는다.** 플랫폼 컴포넌트만 본다.
  고객 A 의 컨테이너만 죽으면 이 페이지는 초록이다. 그 한계를 페이지에 명시해 뒀다.
- **과거를 소급하지 않는다.** 측정 시작일부터만 데이터가 있다.
  2026-08-01 장애 등 그 이전 건은 가동률이 아니라 포스트모템 글로 다뤄야 한다.

## 인시던트 이력 (`docs/incidents.json`)

**프로브가 자동으로 쓰고, 사람이 덧붙인다.**

프로브는 `auto: true` 가 붙은 것만 만들고 닫는다. 사람이 쓴 글은 읽지도 고치지도 않는다.
파일이 없거나 `[]` 이면 페이지에 "보고된 인시던트가 없습니다" 로 표시된다.

### 자동 기록

| | |
|---|---|
| 언제 여나 | 한 컴포넌트가 **연속 3회**(약 30분) 실패했을 때 |
| 언제 닫나 | 그 컴포넌트가 다시 200 을 냈을 때 |
| 시작 시각 | 마지막으로 성공한 다음 회차 (`downSince`) |
| 묶음 | **컴포넌트마다 따로.** 여러 개가 같이 죽으면 글도 여러 개다 |
| 보관 | 끝난 자동 기록은 180일 뒤 지운다. 사람이 쓴 건 안 지운다 |

연속 3회를 기다리는 이유는 배포 중 한두 번 튀는 걸로 고객에게 장애 공지를 띄우지 않기 위해서다.
반대로 30분이 지나도록 안 돌아오면 그건 고객이 이미 겪고 있는 일이다.

컴포넌트마다 따로 여는 이유는 **회복 시점이 제각각**이기 때문이다.
하나로 묶으면 "언제 끝났는지" 가 뭉개진다.

```
관리 콘솔이 3회 연속 응답하지 않았습니다. 확인된 증상은 HTTP 503입니다.
에그호스팅 밖에서 하는 자동 점검에서 감지했습니다.

관리 콘솔이 정상 응답을 재개했습니다. 약 40분 동안 응답하지 않았습니다.
```

**사실만 적는다.** 새벽 3시에 자동으로 열린 글에 "조치 중입니다" 라고 쓰면 그건 거짓말이다.
사연·원인·재발 방지는 사람이 나중에 `updates` 에 덧붙인다. 제목도 고쳐도 된다 —
프로브는 닫을 때 `resolvedAt` 과 업데이트 한 줄만 더한다.

**응답 지연은 인시던트를 열지 않는다.** 막대에 노랑으로 남을 뿐이다.
느린 것과 안 되는 것은 다르고, 느리다고 공지를 띄우면 공지가 값싸진다.

**점검 주소가 틀렸을 때도 열지 않는다.** 한 번도 200 을 받은 적 없는 컴포넌트의 404 는
측정 불가라 애초에 실패로 세지 않는다(위 절 참고).

### RSS

페이지의 「알림 받기」 는 `docs/feed.xml` 이고, 그 피드는 이 파일에서 만들어진다.
자동 기록이 붙기 전에는 이 파일이 늘 비어 있어서, **진짜 장애가 나도 구독자에게
아무것도 가지 않았다.** 이제 열릴 때와 닫힐 때 모두 피드에 실린다.

```json
[
  {
    "title": "관리 콘솔 접속 불가",
    "impact": "major",
    "startedAt": "2026-07-31T15:00:00Z",
    "resolvedAt": "2026-08-01T02:00:00Z",
    "updates": [
      { "at": "2026-07-31T15:20:00Z", "status": "investigating",
        "body": "관리 콘솔과 API 응답이 중단된 것을 확인하고 원인을 찾고 있습니다." },
      { "at": "2026-08-01T02:00:00Z", "status": "resolved",
        "body": "서비스가 정상 복구되었습니다." }
    ]
  }
]
```

- 시각은 전부 **UTC ISO 8601**. 화면에서 KST 로 변환해 보여준다.
- `impact`: `major`(전체 장애) · `partial`(부분 장애) · `degraded`(성능 저하) · `none`(정보)
- `status`: `investigating` · `identified` · `monitoring` · `resolved`
- `resolvedAt` 이 없으면 "진행 중" 으로 표시된다.
- 최신 건이 위로 온다(`startedAt` 내림차순).

⚠️ 이 파일에 적는 내용은 **고객에게 공개되는 대외 문구**다. 원인·책임 표현을 넣기 전에
내부 확인을 거칠 것. 2026-08-01 건(egg-api 9시간 30분 중단)이 1호 소재다.

### 확인

장애를 실제로 내 볼 수는 없으니, 프로브 사본이 우리가 조종하는 서버를 보게 하고
그 서버를 죽였다 살린다.

```bash
node tools/check-incidents.mjs
```

여는 시점·닫는 시점·중복 방지·사람 글 보존·측정 불가일 때 안 여는 것·RSS 반영까지 본다.

## 가동률(%) 표시 스위치

`docs/index.html` 상단 `SHOW_UPTIME` 이 스위치다. 기본값은 `false`.

- `false` — 90일 바는 그리되 "99.87%" 같은 **숫자는 표시하지 않는다**
- `true` — 컴포넌트별 최근 90일 가동률을 숫자로 표시한다

2026-08-19 결정: 수집은 계속하되 숫자는 공개하지 않는다. 유료 MRR 의 79% 가
단일 고객(전용서버)이라, 보상 기준을 문서로 정하기 전에 가동률을 숫자로 내걸면
사실상 SLA 를 약속하는 것이 되기 때문이다. 기준이 문서화되면 이 값만 바꾸면 된다.
